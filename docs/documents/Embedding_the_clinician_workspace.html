    Embedding the clinician workspace

    <natzar-provider> puts the Natzar clinician workspace inside your portal: your clinicians sign in to your app, and your server tells us which clinician they are. The element renders an iframe served from a dedicated provider origin. The clinical UI, the patient data and the session credential stay inside that frame; your page receives only ids, counts and states.

    This guide is the integration contract. It is stricter than the patient embed on purpose: sessions are short-lived and renewed by your server, never put in a URL, bound to one clinician, one parent origin and one partner, and revocable at any time.

    Release status. The provider embed is enabled per partner by an explicit policy (absent policy = disabled). In this release the scoped clinical reads are available. Replies, completion, uploads, referrals, prescriptions, cancellation and availability are implemented but not yet released: Natzar lists them in no partner policy until their release gate passes (signing referrals and prescriptions additionally waits for a staging verification), so a session cannot hold them and an optional request for one comes back in the grant's unavailable list (not_in_policy). Video, readiness and presence are disabled (see Live calls); patient mode is disabled. The tables below say which capability is available today.

    Quickstart

    Load the loader from the provider origin (a classic script) and place the element once, in your persistent app shell:

    <script src="https://PROVIDER_EMBED_ORIGIN/provider/v1/embed.js"></script>
    <natzar-provider id="care" theme="auto" locale="en"></natzar-provider>

    const care = document.querySelector('#care');
    await customElements.whenDefined('natzar-provider');
    await care.connect({
      getSession: async ({sessionId, signal}) => {
        // YOUR endpoint. It derives the clinician from YOUR authenticated server
        // session, checks CSRF, and mints or renews server-to-server.
        const response = await fetch('/api/natzar/provider-session', {
          method: 'POST',
          signal,
          credentials: 'same-origin',
          headers: {'Content-Type': 'application/json', 'X-CSRF-Token': csrfToken()},
          body: JSON.stringify({sessionId}),
        });
        if (!response.ok) throw new Error('Provider session unavailable');
        return response.json();
      },
    });

    The browser sends only {sessionId} (null to start, the current id to renew). Never send a physician id from the browser, and never ship an endpoint that mints a session for a submitted physician id.

    Which host

    Each deployment (environment and residency zone) has its own provider origin and provider API. Read both from the deployment outputs (custom.providerEmbed in amplify_outputs.json: origin, apiUrl, zone, environment, and hosting.loaderUrl / hosting.frameBaseUrl once hosting is enabled), or ask your Natzar contact.

    • Load the loader only from https://<provider origin>/provider/v1/embed.js (or a pinned release, see Pinned loader releases and SRI). A copy served from your own origin is refused.
    • Your server calls https://<api host>/<stage>/provider-embed/...: the apiUrl of the same deployment.
    • The grant tells the loader which frame URL and API URL to use; both belong to the deployment and are checked by the loader and the frame. A grant for another deployment or zone is refused.

    Minting on your server

    Two server-only routes, called with your current partner API key (Authorization: Bearer pp_live_…):

    • POST /v1/provider-embed/sessions mints a logical session: {mode, clinician, parentOrigin, capabilities, optionalCapabilities?, maxAbsoluteSeconds?, idleTimeoutSeconds?, clinicianToken?} (plus resource for a narrow consultation session). It answers 201 with the grant.
    • POST /v1/provider-embed/sessions/{sessionId}/renew rotates the credential of that session: {clinician, clinicianToken?}. It answers 200 with a new grant for the same session, scope and clinician.
    • DELETE /v1/provider-embed/sessions/{sessionId} revokes it (204).

    Rules your endpoint must follow:

    • Current key only. Minting and renewing are refused with a key that is inside the legacy rotation grace window. This is stricter than the rest of the partner API: rotate, deploy the new key, then rotate the provider sessions.
    • Server-side mapping. Decide clinician ({externalPhysicianId} for API-provisioned clinicians, or {physicianId}) from your own login. The request body from the browser is {sessionId} and nothing else.
    • Checks before every mint and renew: the login is valid and unexpired (otherwise answer 401 and DELETE every session that login minted), the user's role is a clinician role, the user belongs to the tenant that may embed, and your MFA requirement is satisfied.
    • Lifetimes. Send maxAbsoluteSeconds = min(28800, seconds left in your login); below 300 ask the user to sign in again. Send your idle policy as idleTimeoutSeconds (60–900). Both can only shorten what the policy allows.
    • CSRF. Your endpoint is cookie-authenticated: require your CSRF token and the exact Origin of your portal.
    • Cache-Control: no-store on the grant response. Never log the grant, the token or the key.
    • Offboarding and logout. Keep a server-side map from your login to every session id it minted. Renew only those; DELETE all of them at logout and when you offboard a clinician.

    The server-only header rule

    The mint, renew and revoke routes refuse any request that carries Origin, Sec-Fetch-Site or Sec-Fetch-Dest: those come from a browser, and these routes are for your server only. Call them with Node's global fetch (or any server HTTP client) and build the headers yourself. Node's own sec-fetch-mode: cors is expected and accepted. Never proxy the browser's headers to Natzar.

    MFA assumptions

    • Delegated mode (you assert the clinician) does not verify MFA. Your login is the clinician's authentication: enforce MFA there before you mint or renew.
    • Verified mode (you relay the clinician's current Natzar ID token as clinicianToken, refreshed on each renew): the production user pool requires MFA; non-production pools do not. The ID token carries no MFA claim, so verified mode proves the clinician's Natzar login, not a particular second factor.

    Modes, scope and capabilities

    A session has one immutable scope, fixed at mint:

    Mode Scope Use
    workspace the clinician's own work Inbox, agenda and the clinician's consultations
    consultation one consultation ({kind, consultationId}) A narrow session for one case of yours
    patient one patient Disabled in this release

    Capabilities are named, never wildcards. A session holds session ∩ policy ∩ deployment ∩ tenant features, checked on every request. Required capabilities that cannot be granted make the mint fail (403 capability_not_granted); optional ones are reported in the grant's unavailable list with a reason.

    Capability What it allows Availability
    workspace.read Workspace lists Available
    consult.read Consultation lists, detail, messages, clinical actions Available
    appointments.read Own agenda Available
    attachments.read Short-lived file grants for the episode's attachments and documents Available
    patient.read Patient identity (name, date of birth) on the clinician's own episodes Not yet available (patient-mode stage); without it lists and details show "Patient details not available"
    consult.reply, consult.complete, attachments.write Replies (accepted for delivery, then delivered), resolve/close, one attachment per reply Not yet released (implemented; in no partner policy until its release gate passes)
    referrals.preview, referrals.issue Referral preview and signing Not yet released (implemented; signing also waits for a staging verification)
    prescriptions.preview, prescriptions.issue Prescription preview and signing (fax zones only) Not yet released (implemented; signing also waits for a staging verification)
    appointments.cancel, availability.write Cancel an own booked appointment that has not started; own async availability Not yet released (implemented; in no partner policy until its release gate passes)
    telehealth.join, telehealth.end, presence.write Video, readiness, presence Disabled (media revocation not proven)
    patient.history.read Longitudinal history Disabled (patient mode)

    Prescribing is offered only where the zone's transport is fax; in zones that use electronic prescribing it is unavailable (transport_unsupported). Consultation escalation is not part of the provider embed.

    Policy defaults, ranges and who may change them

    Your Natzar tenant administrator sets the policy per partner; Natzar operators can disable a partner or every partner.

    Setting Default Range
    Enabled off (no policy = disabled) —
    Allowed parent origins none 1–10 exact origins (https://host[:port]), no wildcards
    Delegation verified delegated, verified or either
    Access credential lifetime 300 s 60–300 s
    Absolute session lifetime 28 800 s (8 h) 900–28 800 s
    Idle lock 900 s (15 min) 60–900 s
    • Every policy change revokes the sessions minted under the previous version.
    • Delegated mode is limited to API-provisioned clinicians (those you created through the partner API).
    • If your partner's physician assertion is switched off, delegated minting keeps working only when the administrator acknowledged that while it was off; an acknowledgement given earlier does not count.

    Security model

    • Trusted delegation. In delegated mode Natzar trusts your server's statement of who the clinician is. Protect the mint endpoint like a login: CSRF, exact origin, server-side mapping, role, tenant and MFA checks.
    • Host page CSP. Allow the provider origin in script-src and frame-src only; the frame needs nothing else from your page. connect-src 'self' is enough for your own endpoint.
    • Origin binding. A session is bound to one exact parent origin and one partner. The loader refuses a grant for another origin; the frame refuses a grant for another partner. Origin binding cannot stop code already running on your page: keep your page free of third-party script you do not trust.
    • No tokens in URLs. The credential travels only in a postMessage to the exact frame origin and in the frame's Authorization header. It is never in a URL, an attribute, storage, a cookie or an event.
    • Stolen-token replay. A stolen access credential works until it expires (≤ 300 s), the session is revoked, or the idle lock triggers; after a renewal the previous secret stops working after 30 s. Revoke promptly.

    Host headers

    • To delegate camera and microphone (once video is enabled), send Permissions-Policy: camera=(self "<provider origin>"), microphone=(self "<provider origin>") on your page, and delegate at every nesting level if your portal is itself framed.
    • Pages that send Cross-Origin-Embedder-Policy: require-corp are not supported.
    • The provider API's web application firewall blocks by request rate only; it never serves a challenge page.

    Framing and permissions

    • The frame is served with frame-ancestors set to exactly your policy's origins, and Cache-Control: no-store: a policy change applies to the very next frame load. Every ancestor counts: your allowed page framed by a page that is not in the policy is refused.
    • An unknown partner, a disabled policy or a kill switch gets the same error page with frame-ancestors 'none'.
    • The loader creates the iframe with the sandbox tokens allow-scripts allow-same-origin allow-forms allow-downloads, referrerpolicy no-referrer, and the permission list fullscreen (plus camera; microphone only when video is enabled for the deployment).
    • Do not wrap the element in your own sandboxed or credentialless iframe.

    Element API

    Member Description
    connect({getSession}) Establish the connection. getSession({sessionId, reason, signal}) returns a grant from your server.
    navigate(target) Select a view inside the grant ({view: 'workspace'} or {kind, consultationId}); resolves {ok} or a reason.
    refresh(grant) Hand over a renewal of the same session yourself (optional; the loader renews by itself).
    canLeave() {canLeave, dirty, inCall} for your navigation guard; never draft content.
    disconnect() Release this instance (not a logout).
    logout() Revoke the session, lock and clear the UI; resolves {revoked}. Your backend logout still revokes independently.
    state disconnected, bootstrapping, authenticating, ready, renewing, locked, revoked or failed.

    Attributes theme (light, dark, auto), locale (en, es, de, fr, it), accent (#rgb/#rrggbb), radius (0–24) and density (comfortable, compact) apply in place; the frame never reloads for them.

    Events

    CustomEvents named natzar:provider:<name> on the element (not bubbling). Details carry ids, counts and states only.

    Event Detail
    ready {sessionId, mode, protocolVersion}
    error {code, recoverable, correlationId?}
    expired {reason: 'access' | 'absolute' | 'idle' | 'revoked'}
    unread-change {count} (workspace mode)
    navigation-request {target}
    consultation-completed {kind, consultationId, outcome}
    call-state-change {consultationId, state}
    dirty-state-change {dirty}
    disconnected {reason: 'host' | 'logout' | 'revoked' | 'protocol_error' | 'failed'}

    The patient embed's events use the prefix natzar:; a listener that matches every natzar: event sees both.

    Behavior notes

    • ready can fire more than once for one element (after an idle-lock reconnect or a frame reload); treat it as "live again", not as a first connection.
    • Moving the element with Element.moveBefore() keeps the connection. Removing it, or re-appending it elsewhere, disconnects (disconnected {host}); call connect() again afterwards.
    • Loading the loader twice is harmless: the first definition wins. The element class exposes loaderVersion and loaderOrigin for diagnostics.

    Lifecycle

    • The access credential lasts ≤ 300 s (policy). The loader asks your getSession to renew about 60 s before expiry, never more often than every 30 s, with bounded retries.
    • The logical session ends at its absolute expiry (≤ 8 h); renewal never extends it.
    • After the idle timeout (≤ 15 min) the frame locks and clears clinical content; the clinician continues with a button, which starts a new session through your getSession.
    • After a renewal the previous secret keeps working for 30 s, so requests in flight complete.
    • A revoked session clears everything and shows guidance without retrying.

    Live calls

    Video, readiness and presence are disabled in this release: the media revocation guarantees have not been proven against the deployed media service, so no policy may grant telehealth.join, telehealth.end or presence.write. Appointments are still listed. When video is enabled in a later release, keep the element mounted during calls: removing it ends the call.

    Presence ownership and the shared presence record

    A clinician's presence ("ready for calls") is one shared record, also used by the standalone portal. When presence is enabled, one provider session at a time owns it through a lease; another tab or session cannot clear a presence it does not own. Presence is disabled in this release together with video.

    Residual signed-file limitations

    Files open through short-lived signed URLs (≤ 60 s) issued to the frame. A signed URL cannot be recalled before it expires, and bytes a clinician downloaded stay on their device after the session ends.

    session_callback_failed yes Your getSession failed
    session_grant_invalid yes Your getSession returned an invalid grant

    What a provider session may call

    The frame calls these browser routes with the session credential; your server calls the three server routes. The server decides every request; the frame only hides what it cannot do. Natzar keeps a route-by-route authorization table tied to its tests for every row below.

    Route Capability
    POST /v1/provider-embed/sessions, …/sessions/{id}/renew, DELETE …/sessions/{id} your server, current API key
    GET /v1/provider-embed/session, POST …/session/activity, POST …/session/logout the session itself
    GET /v1/provider-embed/workspace workspace.read
    GET /v1/provider-embed/agenda appointments.read
    GET /v1/provider-embed/consultations, …/consultations/{kind}/{id}, …/async/{id}/messages, …/async/{id}/clinical-actions consult.read
    GET …/consultations/{kind}/{id}/files/{fileId} attachments.read
    POST …/async/{id}/replies · …/resolve, …/close · …/uploads, …/finalize consult.reply · consult.complete · attachments.write (not yet released)
    POST …/async/{id}/referrals/preview, …/referrals · …/prescriptions/preview, …/prescriptions referrals.* · prescriptions.* (not yet released)
    POST …/telehealth/{id}/cancel · POST /v1/provider-embed/availability appointments.cancel · availability.write (not yet released)
    POST …/telehealth/{id}/room, …/ready, …/end · POST …/presence, …/heartbeat media capabilities (disabled)
    GET /v1/provider-embed/patient, …/patient/history patient mode (disabled)

    Idempotency-Key usage

    Clinical mutations (replies, resolve, close, referral and prescription issue, appointment cancel and call end) require an Idempotency-Key header of 16–128 URL-safe characters. The frame mints one per user action and reuses it for retries of that action, so a double click, a lost response or a retry produces one result. Reusing a key with a different body answers 409 idempotency_conflict; a key whose first request is still running answers 409 idempotency_in_progress. A replayed response carries Idempotent-Replayed: true. Your server never sends these requests; the frame does.

    Pinned loader releases and SRI

    /provider/v1/embed.js is updated compatibly. If you need deterministic updates, load a pinned release /provider/v1/embed.<version>.js with its published integrity value and crossorigin="anonymous". Each release lists its file, integrity (sha384-…) and size. A pinned loader still obeys the current server policy.

    Samples and the patient-switch recipe

    The repository's two-origin harness (scripts/provider-embed-harness/) contains a complete customer backend sample (customer-backend.ts: CSRF, server-side mapping, lifetime clamp, offboarding, verified mode, Node fetch), a plain HTML sample (samples/plain.html, samples/plain.js) and a React sample (samples/react-example.tsx with samples/natzar-provider.d.ts).

    Patient switch. A narrow consultation session is bound to one case for its whole life. To show another case or patient: disconnect() the element, have your backend revoke the previous narrow session and mint one for the new case (after checking the user may open it), and connect() again. Never reuse a session across patients.

    React StrictMode mounts effects twice in development, so the first connect() mints an orphan session that is never used; your backend revokes it at logout from its login-to-sessions map.

    EHR task on resolve

    Resolving a consultation from the embed does not create an EHR task. This matches the partner REST API: create the task from your own system if you need one.
