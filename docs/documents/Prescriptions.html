    Prescriptions — the patient's pharmacy choice

    A physician writing on an async consult can issue a prescription without leaving the thread. What the patient then has to do is choose the pharmacy it goes to — and a partner rendering its own chat has to offer that choice, because the platform's public /pharmacy page refuses consults that belong to a partner. This guide is the whole loop: detect the link, resolve it, list pharmacies, choose one, watch the outcome.

    Everything below assumes the getting-started setup:

    export NATZAR_API="https://<your-assigned-api-host>"
    export NATZAR_KEY="pp_test_..."

    The embed widget (<natzar-async>, <natzar-agent>) does all of this itself — the routes here exist for the headless integration.

    1. What lands on the transcript

    Four system notices, all ordinary async_consult.message events (there is no prescription event type — your existing webhook handler already receives them), distinguished by their classification:

    Classification When What the body carries
    async:prescription_issued The physician signed the prescription. The pharmacy link <host>/pharmacy?id=<prescriptionId> and its validity ("active for the next 24 hours").
    async:prescription_sent The transport delivered it. The pharmacy's name.
    async:prescription_failed The transport gave up after its retries. The pharmacy's name and the link again — the choice is re-opened.
    async:prescription_revoked The physician withdrew it. —

    Detect the link with PHARMACY_LINK_REGEX: group 1 is the prescription id, the whole match is the URL to strip from the prose before you render the message — the same treatment as the consent, video and booking links:

    import {PHARMACY_LINK_REGEX} from '@natzar/client/contract';

    const m = PHARMACY_LINK_REGEX.exec(message.body);
    if (m) {
      const prescriptionId = m[1];
      const text = message.body.replace(m[0], '').trim();
      // render `text` + a "Choose your pharmacy" button bound to prescriptionId
    }

    (The runtime contract symbols live at @natzar/client/contract; the package root exports only their types. The root's detectLink, stripLink and pharmacyActionFor do the same detect-and-strip without the raw regex — see the SDK README.)

    2. Resolve the link

    curl -s "$NATZAR_API/v1/prescriptions/aB3xK9mQpZ4r" \
      -H "Authorization: Bearer $NATZAR_KEY"

    {
      "prescription": {
        "id": "aB3xK9mQpZ4r",
        "externalPatientId": "pat-001",
        "consultId": "kQ7wN2pT9xLm",
        "status": "awaiting_pharmacy",
        "expired": false,
        "expiresAt": "2026-09-19T09:30:00.000Z",
        "transport": "fax",
        "pharmacyName": null,
        "action": "choose",
        "createdAt": "2026-09-18T09:30:00.000Z"
      }
    }

    Render from action ( PharmacyLinkAction); it is decided server-side from the effective state, so your screen, the app and the widget can never disagree:

    action Button Actionable
    choose "Choose your pharmacy" yes — open the picker (§3–4)
    sent "Sent to {pharmacyName}" (or "Sent") no
    expired "Link expired" no
    revoked "Withdrawn" no

    Keep the button visible for the non-actionable values, with the label saying what happened. A prescription of yours whose 24-hour link lapsed answers action: 'expired', not a 404 — the state read is a probe your chat fires for every pharmacy link it renders, and a dead link is an ordinary answer. 404 not_found means the id is not a prescription of this tenant (or of a patient you provisioned).

    GET /v1/patients/state also carries the newest prescription still waiting for a choice as prescription, so a screen opening cold can offer the picker without first scanning the transcript.

    3. List the pharmacies

    curl -s "$NATZAR_API/v1/prescriptions/aB3xK9mQpZ4r/pharmacies?lat=45.4215&lng=-75.6972&source=device" \
      -H "Authorization: Bearer $NATZAR_KEY"

    {
      "prescription": {"id": "aB3xK9mQpZ4r", "action": "choose", "...": "..."},
      "origin": {"lat": 45.4215, "lng": -75.6972, "source": "device"},
      "pharmacies": [
        {
          "directoryId": "ca:ON:305123",
          "name": "Shoppers Drug Mart",
          "address": "1 Rideau St",
          "city": "Ottawa",
          "region": "ON",
          "postalCode": "K1N 8S7",
          "phone": "+16135550100",
          "reachable": true,
          "lat": 45.4262,
          "lng": -75.6925,
          "distanceKm": 0.6
        }
      ]
    }

    The list is ranked by distance from the origin, resolved in this order — the same order the platform's own picker uses:

    1. What you pass: lat/lng (both or neither), with source saying how you got it (device for geolocation, manual for a typed place, address for a home address you geocoded) and an optional label. A pair that is not a place on Earth (latitude beyond ±90, longitude beyond ±180, or 0,0) is 422 invalid_location — never silently replaced by the cached home.
    2. The patient's cached home, when the platform holds one (see §5).
    3. Nothing — the response has no origin, the list is unranked, and homeAddress carries the patient's one-line address on file for you to geocode; store the result with POST …/home-location and the next search (yours, the app's, the widget's) starts from it.

    query filters by name, city or postal code; radiusKm widens the search in the steps of PHARMACY_SEARCH_RADII_KM (25, 50, 100 — "search wider"). reachable: false means the transport cannot deliver there (a fax jurisdiction with no verified fax line on file): show it greyed out, or not at all — choosing it is 409 pharmacy_unreachable.

    Once the prescription is no longer choosable the list is empty and prescription.action says why — render that instead of an empty picker.

    4. Choose

    curl -s -X POST "$NATZAR_API/v1/prescriptions/aB3xK9mQpZ4r/pharmacy" \
      -H "Authorization: Bearer $NATZAR_KEY" -H 'Content-Type: application/json' \
      -d '{"directoryId": "ca:ON:305123"}'

    {"prescription": {"id": "aB3xK9mQpZ4r", "status": "transmitting", "pharmacyName": "Shoppers Drug Mart", "action": "sent", "...": "..."}}

    The choice is atomic — one conditional transition shared with every other surface — so a choice from your screen and one from the widget cannot both succeed. The loser gets 409 prescription_not_choosable with the effective status in details; the same code answers a lapsed link and an already-settled prescription. Re-read GET /v1/prescriptions/{id} and render its action. 404 pharmacy_not_found is a directoryId no listing of this deployment produced.

    Then watch the outcome: poll GET /v1/prescriptions/{id} until status is sent or failed, or simply keep rendering the transcript — prescription_sent names the pharmacy; prescription_failed re-opens the choice (action is choose again, with the link in the body).

    5. Cache the home location

    When you geocoded the patient's home address (homeAddress from §3, or an address they typed), hand the point back so no surface has to geocode it again:

    curl -s -X POST "$NATZAR_API/v1/prescriptions/aB3xK9mQpZ4r/home-location" \
      -H "Authorization: Bearer $NATZAR_KEY" -H 'Content-Type: application/json' \
      -d '{"lat": 45.4215, "lng": -75.6972}'

    {"ok": true}, or 422 invalid_location for coordinates that are not a place on Earth. The write is gated on a prescription you can see, so it is only reachable from a live picker.

    6. A pharmacy the directory does not list

    Fax jurisdictions only (transport: 'fax'): the directory is the platform's own, fed by the provincial registers, and a pharmacy may be missing from it. The patient can add one:

    curl -s -X POST "$NATZAR_API/v1/prescriptions/aB3xK9mQpZ4r/pharmacies" \
      -H "Authorization: Bearer $NATZAR_KEY" -H 'Content-Type: application/json' \
      -d '{"name": "Pharmacie du Coin", "address": "12 rue Principale", "city": "Gatineau", "region": "QC", "postalCode": "J8X 1A1", "fax": "(819) 555-0199"}'

    {
      "pharmacy": {"directoryId": "ca:manual:7hQ2pL9x", "name": "Pharmacie du Coin", "reachable": false, "...": "..."},
      "status": "pending_verification",
      "probe": "sent",
      "faxIssue": null
    }

    201: the pharmacy now exists (reachable: false) and appears in searches at once. The prescription is not chosen for it yet — no prescription is ever faxed to an unverified line. probe: 'sent' means the platform has dispatched a one-page verification fax to the line; the moment the line acknowledges it, the platform chooses this pharmacy for the prescription on its own (poll GET /v1/prescriptions/{id} — the state moves to action: 'sent'). probe: 'not_sent' means no line to verify: the fax was missing or dropped (faxIssue), and a clinician adds it from the portal. Tell the patient the pharmacy is being verified; until then the prescription stays choosable, and they may still pick a listed pharmacy instead.

    409 pharmacy_add_unavailable on an e-prescribed prescription (the network already lists every pharmacy it can reach) or a deployment without a directory; 409 prescription_not_choosable once settled; 422 invalid_pharmacy with details.code when the address cannot be placed in a province; faxIssue (same_as_phone, toll_free, invalid) when the fax line as typed was dropped while the rest was kept.

    What this surface deliberately does not do

    • No clinical content. PrescriptionResource is the link state: what was prescribed is between the physician and the pharmacy.
    • No listing. A prescription is reached by the id in its transcript link, or as prescription on GET /v1/patients/state.
    • Physician sessions cannot call these routes — they are patient-side, tenant-key only (403 forbidden to a session).

    In an erx deployment the pharmacy search is answered by the e-prescribing network, in a fax one by the platform's own directory — the same search, with the same credentials, the platform's /pharmacy page and app run.
