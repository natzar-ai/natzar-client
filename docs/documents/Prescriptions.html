    Prescriptions — physician issue and patient pharmacy choice

    A physician writing on an async consult can issue a prescription without leaving the thread. What the patient then has to do is choose the pharmacy it goes to — and a partner rendering its own chat has to offer that choice, because the platform's public /pharmacy page refuses consults that belong to a partner. This guide is the whole loop: detect the link, resolve it, list pharmacies (after the delivery-address step, in an e-prescribing deployment), show the list's licensure notice and distances, choose one, watch the outcome.

    Everything below assumes the getting-started setup:

    export NATZAR_API="https://<your-assigned-api-host>"
    export NATZAR_KEY="pp_test_..."

    The embed widget (<natzar-async>, <natzar-agent>) does all of this itself — the routes here exist for the headless integration.

    Patients under 18

    In both US and Canadian prescribing, include the actual patient's measured height, weight and both measurement dates in the physician's prescription draft:

    "measurements": {
      "heightCm": 140.5,
      "weightKg": 34.2,
      "heightObservationDate": "2026-10-18",
      "weightObservationDate": "2026-10-19"
    }

    Dates must be real calendar dates, no earlier than the patient's birthdate and not in the future. Missing or implausible measurements refuse signing with invalid_request and reason pediatric_measurements_unavailable; correct the measurements and retry. This requirement ends on the patient's 18th birthday. Use the child's clinical identity when prescribing for a child, even if an adult requested care. US transmission converts the signed metric originals into LogiCoy's integer pounds and feet/inches; Canadian fax documents show the metric originals and both dates.

    1. What lands on the transcript

    Prescription outcome notices, all ordinary async_consult.message events (these outcomes have no separate prescription event type — your existing webhook handler already receives them; pharmacy requests have their own event below), distinguished by their classification:

    Classification When What the body carries
    async:prescription_issued The physician signed the prescription. The pharmacy link <host>/pharmacy?id=<prescriptionId> and its validity ("active for the next 24 hours").
    async:prescription_sent The transport delivered it. The pharmacy's name.
    async:prescription_failed The transport gave up after its retries. The pharmacy's name and the link again — the choice is re-opened.
    async:prescription_revoked The physician withdrew it. —
    async:prescription_partially_sent Some medication lines reached the network and others did not. Outcome summary, no pharmacy link.
    async:prescription_delayed Send is held for prescriber readiness recovery. Clinic follow-up information, no new choice link.
    async:prescription_contact_clinic A prescription-scoped failure requires physician action. Contact instruction; the old link is expired.

    Detect the link with PHARMACY_LINK_REGEX: group 1 is the prescription id, the whole match is the URL to strip from the prose before you render the message — the same treatment as the consent, video and booking links:

    import {PHARMACY_LINK_REGEX} from '@natzar/client/contract';

    const m = PHARMACY_LINK_REGEX.exec(message.body);
    if (m) {
      const prescriptionId = m[1];
      const text = message.body.replace(m[0], '').trim();
      // render `text` + a "Choose your pharmacy" button bound to prescriptionId
    }

    (The runtime contract symbols live at @natzar/client/contract; the package root exports only their types. The root's detectLink, stripLink and pharmacyActionFor do the same detect-and-strip without the raw regex — see the SDK README.)

    2. Resolve the link

    curl -s "$NATZAR_API/v1/prescriptions/aB3xK9mQpZ4r" \
      -H "Authorization: Bearer $NATZAR_KEY"

    {
      "prescription": {
        "id": "aB3xK9mQpZ4r",
        "externalPatientId": "pat-001",
        "consultId": "kQ7wN2pT9xLm",
        "status": "awaiting_pharmacy",
        "expired": false,
        "expiresAt": "2026-09-19T09:30:00.000Z",
        "transport": "fax",
        "pharmacyName": null,
        "action": "choose",
        "addressRequired": false,
        "createdAt": "2026-09-18T09:30:00.000Z"
      }
    }

    Render from action ( PharmacyLinkAction); it is decided server-side from the effective state, so your screen, the app and the widget can never disagree:

    action Button Actionable
    choose "Choose your pharmacy" yes — open the picker (§3–5)
    sent "Sent to {pharmacyName}" (or "Sent") while transmission is in progress no
    change "Change pharmacy" after delivery yes — open the authenticated embed's pharmacy view for a pharmacy-led transfer handoff; this never authorizes a new send
    expired "Link expired" no
    revoked "Withdrawn" no

    Keep the button visible for the non-actionable values, with the label saying what happened. A prescription of yours whose 24-hour link lapsed answers action: 'expired', not a 404 — the state read is a probe your chat fires for every pharmacy link it renders, and a dead link is an ordinary answer. 404 not_found means the id is not a prescription of this tenant (or of a patient you provisioned).

    addressRequired: true means the picker will open on the delivery-address step (§4): an e-prescribed prescription (transport: 'erx') with no address confirmed for it yet. It is always false in a fax deployment.

    GET /v1/patients/state also carries the newest prescription still waiting for a choice as prescription, so a screen opening cold can offer the picker without first scanning the transcript.

    3. List the pharmacies

    curl -s "$NATZAR_API/v1/prescriptions/aB3xK9mQpZ4r/pharmacies?lat=45.4215&lng=-75.6972&source=device" \
      -H "Authorization: Bearer $NATZAR_KEY"

    {
      "prescription": {"id": "aB3xK9mQpZ4r", "action": "choose", "...": "..."},
      "origin": {"lat": 45.4215, "lng": -75.6972, "source": "device"},
      "address": {"step": null, "onFile": null, "zipHint": null},
      "preferred": null,
      "licensure": null,
      "distanceUnit": "km",
      "pharmacies": [
        {
          "directoryId": "ca:ON:305123",
          "name": "Shoppers Drug Mart",
          "address": "1 Rideau St",
          "city": "Ottawa",
          "region": "ON",
          "postalCode": "K1N 8S7",
          "phone": "+16135550100",
          "reachable": true,
          "lat": 45.4262,
          "lng": -75.6925,
          "distanceKm": 0.6
        }
      ]
    }

    The list is ranked by distance from the origin, resolved in this order — the same order the platform's own picker uses:

    1. What you pass: lat/lng (both or neither), with source saying how you got it (device for geolocation, manual for a typed place, address for a home address you geocoded) and an optional label. A pair that is not a place on Earth (latitude beyond ±90, longitude beyond ±180, or 0,0) is 422 invalid_location — never silently replaced by the cached home.
    2. The patient's cached home, when the platform holds one (see §4 and §6).
    3. Nothing — the response has no origin, the list is unranked, and homeAddress carries the patient's one-line address on file for you to geocode; store the result with POST …/home-location and the next search (yours, the app's, the widget's) starts from it.

    query filters by name, city or postal code; radiusKm widens the search in the steps of PHARMACY_SEARCH_RADII_KM (25, 50, 100 — "search wider"; always kilometres, whatever the list's distanceUnit — see §4b). reachable: false means the transport cannot deliver there (a fax jurisdiction with no verified fax line on file): show it greyed out, or not at all — choosing it is 409 pharmacy_unreachable.

    Once the prescription is no longer choosable the list is empty and prescription.action says why — render that instead of an empty picker.

    The remembered pharmacy. preferred is the pharmacy the patient's last prescription reached — on any surface: your screen, the widget, the app — resolved even when it falls outside this search (with its distanceKm from the origin). Pre-select it, pinned at the top, so sending to it again is one tap. It is null when there is none, when it can no longer be reached, when it is the pharmacy this prescription just failed at (a re-choice after prescription_failed), and while the address step is pending. The platform learns it by itself when a transmission is delivered; there is nothing to write.

    4. The delivery address (e-prescribing deployments)

    The e-prescribing network receives the patient's full structured address, and the platform's signup asks for a ZIP code only. So in an erx deployment the list answers an address step before its pharmacies — the first time a patient chooses a pharmacy it collects their home address, and for every later prescription it only asks them to confirm it. In a fax deployment address.step is always null and nothing in this section applies.

    {
      "prescription": {"id": "aB3xK9mQpZ4r", "transport": "erx", "action": "choose", "addressRequired": true, "...": "..."},
      "address": {
        "step": "confirm",
        "onFile": {"street": "350 Fifth Avenue", "street2": "Suite 3300", "city": "New York", "state": "NY", "zipCode": "10118", "country": "US"},
        "zipHint": null
      },
      "preferred": null,
      "licensure": null,
      "distanceUnit": "mi",
      "pharmacies": []
    }
    address.step When Show
    collect No home address on file The address form — street, apt/unit (optional), city, state, ZIP — prefilled with zipHint (the patient's ZIP on file, from their signup)
    confirm onFile is the address on file "Yes, use this address", and "Change address" (the same form, prefilled with onFile)
    null A fax deployment, a prescription that can no longer be chosen, or an address already confirmed for THIS prescription (a re-choice after a failure) The list

    While the step is set, pharmacies is empty and no search ran. Answer it with the address — the one typed, picked from your own autocomplete, or onFile sent back unchanged to confirm:

    curl -s -X PUT "$NATZAR_API/v1/prescriptions/aB3xK9mQpZ4r/address" \
      -H "Authorization: Bearer $NATZAR_KEY" -H 'Content-Type: application/json' \
      -d '{"address": {"street": "350 Fifth Avenue", "street2": "Suite 3300", "city": "New York", "state": "NY", "zipCode": "10118"}, "lat": 40.748, "lng": -73.986}'

    The response is the list itself (address.step: null, prescription.addressRequired: false), ranked from lat/lng, with the licensure notice judged against the address just sent (§4a) — so go straight on to the choice (§5). What the platform does with it:

    • Freezes it on this prescription as its delivery address — one atomic write, only while the prescription is waiting for a pharmacy — so a re-choice after a failed transmission never asks again.
    • Saves it as the patient's home address, which every later prescription (on every surface) only asks to confirm, and which moves the patient's state of residence and current ZIP code with it.
    • Caches its point. lat/lng (both or neither — three decimals are plenty) become the patient's home point, the origin of every later search. Without them a NEW address drops the old point (it belonged to the old address) and the list offers homeAddress for you to geocode (§6); the same address confirmed again keeps it.

    The address is judged by the same rule as the platform's own pickers. 422 invalid_address with details.code naming the field to fix ( PrescriptionAddressError): street or city empty (after trimming, or as the network is sent it — nothing left once folded to plain ASCII), a state that is not a US state, DC or inhabited territory code (or a country other than US), a zipCode that is not five digits or ZIP+4, a line over its PRESCRIPTION_ADDRESS_LIMITS limit (street and unit 40, city 35, counted as the network is sent it) (tooLong). Values come back normalised — trimmed, the state uppercase, ZIP+4 as 12345-6789. Leaving out the street, city, state or zipCode key (send "" for a line the patient left blank) or sending a non-string is 400 invalid_request. 422 invalid_location for an off-Earth pair; 409 prescription_not_choosable (with details.status) once the prescription is settled; 409 address_not_applicable on a faxed prescription. Repeating the call while the prescription is choosable writes the same state.

    One call instead of two. When you already hold the address (the patient confirmed it on your screen), send it with the choice:

    curl -s -X POST "$NATZAR_API/v1/prescriptions/aB3xK9mQpZ4r/pharmacy" \
      -H "Authorization: Bearer $NATZAR_KEY" -H 'Content-Type: application/json' \
      -d '{"directoryId": "us:ncpdp:1234567", "address": {"street": "350 Fifth Avenue", "city": "New York", "state": "NY", "zipCode": "10118"}}'

    It is judged first (422 invalid_address), frozen in the same atomic transition as the choice, and saved as the home address once the choice commits (its cached point is kept only when the address is unchanged). Without it, choosing an e-prescribed prescription that has no confirmed address is 409 address_required — run the step, then choose again.

    Autocomplete belongs to your side: the patient types into your page, your autocomplete (Google Places, or any other) runs in their browser, and the platform receives only the submitted address and the point.

    4a. The prescriber-licensure notice

    A prescription is written for the state the patient was in when the physician signed it, under the licence the physician held for the state the consult was opened in (usually the same state). When the delivery address confirmed for it is in a different state than either, your tenant enforces state licensure (see licenseEnforcement on GET /v1/physicians/{id}/licenses), and the prescribing physician holds no usable licence in that state, the list says so:

    {
      "prescription": {"id": "aB3xK9mQpZ4r", "transport": "erx", "action": "choose", "addressRequired": false, "...": "..."},
      "address": {"step": null, "onFile": {"street": "1 Main St", "city": "Hoboken", "state": "NJ", "zipCode": "07030", "country": "US"}, "zipHint": null},
      "preferred": null,
      "licensure": {"state": "NJ", "stateName": "New Jersey"},
      "distanceUnit": "mi",
      "pharmacies": ["..."]
    }

    It is non-blocking. The patient may still choose any pharmacy and send; nothing about the choice (§5) changes. Show it as a calm, informational notice above the list — an info or amber banner, not your error slot, and never a reason to disable a pharmacy or the button. The platform's own pickers word it:

    Your prescribing doctor isn't registered in New Jersey. Most states and pharmacies accept prescriptions from out-of-state doctors, but some pharmacies in some states may refuse it.

    stateName is the English name; when you render another language, localise the state from its two-letter state. The notice names the state only, never a licence.

    licensure is null — show nothing — while the address step is pending (look for it on the PUT …/address response and every read after it), in a fax deployment, once the prescription can no longer be chosen, when the address is in the state the prescription was written for and the licence it was signed under is for that state too, when your tenant does not enforce licensure, when the physician is licensed there, and when the platform could not run the check (it never fails the list for it). An address in the prescription's own state can still carry the notice: a prescription signed under another state's licence (a second prescription after the patient moved, say) is checked against the physician's licences like any other. Read the field on every list rather than only when the state changed. It is computed on every read, so a reload shows it again; there is nothing to store or dismiss server-side.

    4b. Distances and the unit to show them in

    Every list carries distanceUnit: "mi" in the United States deployment, "km" elsewhere. The numbers on the wire stay kilometres — distanceKm on each pharmacy and on preferred, accuracyKm on an ip origin, the radiusKm you send — so convert for display with distanceInUnit (one decimal) from @natzar/client/contract, or divide by KM_PER_MILE (1.609344) yourself:

    import {distanceInUnit, PHARMACY_SEARCH_RADII_KM} from '@natzar/client/contract';

    const distance = (km: number, unit: 'mi' | 'km') => {
      const n = distanceInUnit(km, unit);
      return n === 0 ? `< 0.1 ${unit}` : `${n.toLocaleString(locale)} ${unit}`;
    };
    distance(13.7, 'mi'); // "8.5 mi"
    distance(0.05, 'mi'); // "< 0.1 mi"
    distance(13.7, 'km'); // "13.7 km"

    Label the "search wider" steps in the same unit but keep sending the km value, rounded to the nearest whole unit: radiusKm=25 | 50 | 100 reads as 16 / 31 / 62 mi, as on the platform's own pickers. Round to the nearest, not down: in the United States the search itself covers that many whole miles, so a "15 mi" label would sit above a pharmacy listed at 15.8 mi. Use one formatter for the list, the remembered pharmacy and any map pins, so the same pharmacy never shows two different numbers.

    5. Choose

    curl -s -X POST "$NATZAR_API/v1/prescriptions/aB3xK9mQpZ4r/pharmacy" \
      -H "Authorization: Bearer $NATZAR_KEY" -H 'Content-Type: application/json' \
      -d '{"directoryId": "ca:ON:305123"}'

    {"prescription": {"id": "aB3xK9mQpZ4r", "status": "transmitting", "pharmacyName": "Shoppers Drug Mart", "action": "sent", "...": "..."}}

    The choice is atomic — one conditional transition shared with every other surface — so a choice from your screen and one from the widget cannot both succeed. The loser gets 409 prescription_not_choosable with the effective status in details; the same code answers a lapsed link and an already-settled prescription. Re-read GET /v1/prescriptions/{id} and render its action. 404 pharmacy_not_found is a directoryId no listing of this deployment produced. In an e-prescribing deployment, 409 address_required means the delivery address was never confirmed for this prescription (§4).

    Then watch the outcome: poll GET /v1/prescriptions/{id} until status is sent or failed, or simply keep rendering the transcript — prescription_sent names the pharmacy; prescription_failed re-opens the choice (action is choose again, with the link in the body).

    6. Cache the home location

    When you geocoded the patient's home address (homeAddress from §3, or an address they typed), hand the point back so no surface has to geocode it again (the address step, §4, does the same with its lat/lng):

    curl -s -X POST "$NATZAR_API/v1/prescriptions/aB3xK9mQpZ4r/home-location" \
      -H "Authorization: Bearer $NATZAR_KEY" -H 'Content-Type: application/json' \
      -d '{"lat": 45.4215, "lng": -75.6972}'

    {"ok": true}, or 422 invalid_location for coordinates that are not a place on Earth. The write is gated on a prescription you can see, so it is only reachable from a live picker.

    7. A pharmacy the directory does not list

    Fax jurisdictions only (transport: 'fax'): the directory is the platform's own, fed by the provincial registers, and a pharmacy may be missing from it. The patient can add one:

    curl -s -X POST "$NATZAR_API/v1/prescriptions/aB3xK9mQpZ4r/pharmacies" \
      -H "Authorization: Bearer $NATZAR_KEY" -H 'Content-Type: application/json' \
      -d '{"name": "Pharmacie du Coin", "address": "12 rue Principale", "city": "Gatineau", "region": "QC", "postalCode": "J8X 1A1", "fax": "(819) 555-0199"}'

    {
      "pharmacy": {"directoryId": "ca:manual:7hQ2pL9x", "name": "Pharmacie du Coin", "reachable": false, "...": "..."},
      "status": "pending_verification",
      "probe": "sent",
      "faxIssue": null
    }

    201: the pharmacy now exists (reachable: false) and appears in searches at once. The prescription is not chosen for it yet — no prescription is ever faxed to an unverified line. probe: 'sent' means the platform has dispatched a one-page verification fax to the line; the moment the line acknowledges it, the platform chooses this pharmacy for the prescription on its own (poll GET /v1/prescriptions/{id} — the state moves to action: 'sent'). probe: 'not_sent' means no line to verify: the fax was missing or dropped (faxIssue), and a clinician adds it from the portal. Tell the patient the pharmacy is being verified; until then the prescription stays choosable, and they may still pick a listed pharmacy instead.

    409 pharmacy_add_unavailable on an e-prescribed prescription (the network already lists every pharmacy it can reach) or a deployment without a directory; 409 prescription_not_choosable once settled; 422 invalid_pharmacy with details.code when the address cannot be placed in a province; faxIssue (same_as_phone, toll_free, invalid) when the fax line as typed was dropped while the rest was kept.

    What the patient pharmacy routes deliberately do not do

    • No clinical content. PrescriptionResource is the link state: what was prescribed is between the physician and the pharmacy. The one patient datum the picker reads back is the home address on file (address.onFile), on the list of a prescription you can see, while it can be chosen — the confirmation step cannot be shown without it.
    • No listing. A prescription is reached by the id in its transcript link, or as prescription on GET /v1/patients/state.
    • Physician sessions cannot call these routes — they are patient-side, tenant-key only (403 forbidden to a session).

    In an erx deployment the pharmacy search is answered by the e-prescribing network through the Rx gateway, in a fax one by the platform's own directory. All patient surfaces use the same search/resolve core; your tenant key authenticates Natzar, and vendor credentials stay only in the prescriptions service.

    The physician side: e-prescribing (US)

    SDK 0.20.0 supports native coded US prescribing. Canada continues to accept free-text fax drafts. A US physician must finish network enrollment and app-initiated ID.me in the Natzar portal; routine search/issue then works through the physician API. This is an implemented contract; the current sandbox's fresh-registration and real-send certification gates are still pending (validation record).

    Use one of the physician credentials, not a tenant key alone. On your server, the asserted physician ID header may accompany the key; in a browser use the short-lived physician session and keep the key server-side. Read readiness for the acting physician:

    curl -s "$NATZAR_API/v1/physicians/me/eprescribing" \
      -H "Authorization: Bearer $PHYSICIAN_SESSION"

    eprescribing contains transport, ready, ordered requirements, identity.status/verifiedUntil, portalAccess, setupUrl and pharmacyRequests.{open,dueSoon,inboxUrl}. In Canada readiness is transport configuration and portal/identity/request fields are null. In the US, portalAccess: 'invite_required' means your server must request the normal portal invite before the physician follows setupUrl:

    curl -X POST "$NATZAR_API/v1/physicians/$PHYSICIAN_ID/portal-invite" \
      -H "Authorization: Bearer $NATZAR_KEY"

    The physician completes their own enrollment and ID.me, then rereads readiness. Never hard-code ready, adopt historical vendor IDs, or treat a vendor login as the app's identity proof. Verification needs at least two days remaining on issue. Offer setup/renewal for the returned requirement; network errors should be retried with backoff.

    Search a trimmed query of 3–80 characters:

    curl -s --get "$NATZAR_API/v1/drugs" --data-urlencode 'q=lisinopril' \
      -H "Authorization: Bearer $PHYSICIAN_SESSION"

    The response groups products → strength/form options → packages and reports truncated. Controlled options are visible but must be disabled. Have the physician choose an option and package. Use its ndc, description and option unit for erx; names alone cannot authorize a prescription. A properly segmented NDC query or 11-digit NDC searches the package directly; a bare ambiguous 10-digit number is not a valid substitute.

    Save coded-prescription.json with the draft below, replacing every package placeholder with the chosen search result and confirming directions and quantity with the physician:

    {
      "draft": {
        "items": [{
          "medication": "Lisinopril", "strength": "10 mg", "form": "tablet",
          "dose": "1 tablet", "route": "oral", "frequency": "daily",
          "quantity": "", "refills": 0,
          "erx": {
            "ndc": "<selected 11-digit NDC>",
            "drug": "<selected package description>",
            "unit": "<selected option unit>",
            "quantity": "30", "daysSupply": 30
          }
        }],
        "pharmacistNote": ""
      }
    }

    curl -X POST "$NATZAR_API/v1/async-consults/$CONSULT_ID/prescriptions" \
      -H "Authorization: Bearer $PHYSICIAN_SESSION" \
      -H 'Content-Type: application/json' --data-binary @coded-prescription.json

    The server prepares/rechecks the NDC package and readiness and freezes routing; client drug descriptions/units cannot override the network result. A US uncoded line is 400 invalid_request with details.code: 'item_not_coded'; quantity comes from erx.quantity/unit, days supply is 1–90, and the pharmacist note is ≤210 after ASCII transliteration. A not-ready physician gets 409 prescriber_not_ready with requirements and setupUrl; controlled or unavailable drugs get 422 controlled_substance or drug_unavailable with affected line indexes. A gateway/network outage gives 503 dependency_unavailable; retry after backoff. Canada still requires its free-text quantity.

    A successful issue returns 201 with prescription ID, issue time and pharmacy link. It creates no network draft yet. The patient performs §§1–6: confirms address, chooses pharmacy, and sees the actual send outcome. Street, optional unit and city limits are 40, 40 and 35 characters. Locally accepted ZIP+4 is sent to the US network as its five-digit prefix. A prescription-scoped failure expires the old link; it must not invite another pharmacy choice.

    When a linked Change/Renewal request arrives, the eprescribing.pharmacy_request webhook carries physician/request IDs, kind, receipt/deadline, linked consult/prescription IDs and inboxUrl. Refresh the readiness count and offer that inbox link. Request/medication clinical details remain in the protected portal; only the named physician answers there. Answers do not edit the original prescription or send a patient transcript notice. Unlinked requests are portal-only.
