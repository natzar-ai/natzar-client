    Embedding the patient UI

    Two custom elements let you drop the full Natzar patient experience into your own pages instead of building chat/video UIs yourself:

    • <natzar-async> — the async-consult chat: consent prompt, message thread, attachments, rating sheet. The composer is live as soon as the patient consents — even while the consult is still queued waiting for a physician, the patient can send context (symptoms, photos) and it persists to the transcript as the physician's intake.
    • <natzar-telehealth> — the live video consult: waiting room, camera check, the call itself, rating.

    Quickstart

    Two lines per widget. Load the embed script once, then render the tag with a session token your server minted:

    <script src="https://us.app.natzar.ai/embed/v1/embed.js"></script>
    <natzar-telehealth session-token="…" locale="en" theme="auto"></natzar-telehealth>

    <script src="https://us.app.natzar.ai/embed/v1/embed.js"></script>
    <natzar-async session-token="…" locale="en" theme="auto"></natzar-async>

    Which host

    The script and the widget iframe are served by the Natzar app origin for the environment your API key belongs to. Load the script from the origin matching the key that minted the token — a pp_test_… token will not open in the production widget.

    Environment Embed origin
    prod https://us.app.natzar.ai
    stage https://stage.us.app.natzar.ai
    dev https://dev.us.app.natzar.ai

    @natzar/client carries the same table, so you can build the URL instead of hardcoding it:

    import {resolveEndpoints} from '@natzar/client';

    const {embedOrigin} = resolveEndpoints({environment: 'prod'});
    const src = `${embedOrigin}/embed/v1/embed.js`;

    Getting the token (server-side, with your API key — never in the browser):

    • Telehealth: POST /v1/telehealth-consults/{id}/embed-session
    • Async: POST /v1/async-consults/{id}/embed-session, or take the sessionToken returned directly by POST /v1/async-consults when you create the consult with consent: "embed".

    The response carries {sessionToken, expiresAt}. Tokens are consult-scoped (they open exactly one consult) and short-lived (1 hour by default; ttlSeconds 60–86400 on the mint request). The token's kind must match the tag — a telehealth token in <natzar-async> refuses to load.

    For clinics that charge for a visit, the widget presents a secure card form inside its frame and resumes the consultation after Natzar confirms payment. The host page does not need a checkout redirect, a payment return route or any code: the element gives the form room by itself (see The payment step). It is one press for the patient: the invite reads "Yes & pay CA$100" (or "Join & pay …", "Confirm 3:00 PM · Pay …"), and that press opens the card form directly — see Payments for how the same flow is built without the widget. Natzar deployments that enable this flow must set VITE_STRIPE_PUBLISHABLE_KEY to the publishable key for the same Stripe account as the backend STRIPE_SECRET_KEY. Local Vite development reads it from .env.local; restart Vite after changing that file.

    Requirements & the origin allowlist

    • HTTPS only. The widgets run in an iframe on a secure origin, and the telehealth widget needs getUserMedia — browsers only grant camera and microphone access in a secure context. A plain-HTTP host page cannot run the video widget (localhost is exempt for development).
    • Your page's origin must be allowlisted. The widget verifies the embedding page's origin against your partner account's allowedOrigins list and refuses to load from anywhere else (origin_not_allowed, surfaced as a natzar:error event). Register every origin you embed from — scheme + host + port, e.g. https://portal.your-clinic.com. The check covers the widget's ancestor origins; note that tokens being consult-scoped and short-lived is the primary containment — treat the allowlist as defense in depth, not as a substitute for keeping tokens out of untrusted pages.

    Camera, microphone, location & payment

    The embed script sets allow="camera; microphone; display-capture; geolocation; payment" on the iframe it creates, so no host-page changes are usually needed — the browser prompts the patient inside your page and the stream stays in the iframe. Camera and microphone serve the telehealth call; geolocation serves the pharmacy picker (see Prescriptions below), which offers to use the device's location when the patient has no home address on file — without the delegation the browser refuses silently, and the picker falls back to a coarse IP-based location. payment serves the in-frame checkout: Apple Pay and Google Pay run on the Payment Request API, which a cross-origin frame may only use when delegated, so without it the card form simply offers no wallets.

    The exception: if your embedding page is itself inside an iframe (your page is nested in yet another product), every ancestor frame must also delegate camera/microphone/geolocation/payment via its own allow attribute — permissions policy delegation is per-hop. Same if your site sends a restrictive Permissions-Policy response header: it must not deny camera / microphone / geolocation / payment for the embed to work.

    Attributes

    All attributes are observed — changing one re-renders the widget (changing session-token is equivalent to calling refresh).

    Attribute Required Values Meaning
    session-token yes JWT from /embed-session Which consult the widget shows. Mint server-side only.
    locale no en es de fr it UI language. Default: browser language, falling back to en.
    theme no light dark auto Color scheme. Default auto (follows prefers-color-scheme).

    Element API

    Member Meaning
    refresh(sessionToken) Swap in a freshly minted token without tearing down the widget — the intended reaction to natzar:expired. In-flight calls and a live video call continue uninterrupted.

    Events

    The widget dispatches DOM CustomEvents on the element, named natzar:<event>; the payload is in event.detail (shapes: EmbedEventDetailMap).

    const el = document.querySelector('natzar-async');
    el.addEventListener('natzar:message', (e) => console.log(e.detail.message));
    el.addEventListener('natzar:expired', async () => el.refresh(await mintToken()));
    Event Surface detail When
    natzar:ready both {type, consultId} Widget loaded, verified its token, rendered.
    natzar:consented async {consultId} Patient accepted the consent prompt.
    natzar:queued both {consultId} Waiting for a physician (async: no capacity yet — the chat still accepts messages, which persist for the physician; telehealth: waiting room).
    natzar:assigned both {consultId, physicianName?} A physician took the consult.
    natzar:message async {consultId, message} A new message appeared on the thread (any author) — useful for host-page unread badges.
    natzar:joined telehealth {consultId} The patient entered the live call.
    natzar:ended telehealth {consultId} The call ended (rating step may follow).
    natzar:rated both {consultId, stars?} The patient submitted a rating.
    natzar:closed both {consultId, closedReason?} Terminal state (a declined consent surfaces here with closedReason: 'declined').
    natzar:expired both {consultId} The session token expired; the widget freezes read-only until you refresh(token).
    natzar:error both {code?, message} Something went wrong (invalid token, disallowed origin, network…).
    natzar:payment all {consultId, phase} The payment step opened (phase: 'started') or closed ('ended' — paid, backed out of, failed, expired, or the frame reloaded). The element shows the step as a dialog on its own; cancelable — see The payment step.

    The payment step

    When the clinic charges for a visit, the widget swaps its conversation for a Stripe checkout — straight from the patient's first press on the priced invite, which already names the amount. A frame sized for a chat is cramped for a checkout, so for as long as the step is open the element presents itself as a modal dialog over your page — a large centered panel on desktop, a bottom sheet on phones — and puts itself back when the step closes: paid, backed out of (the step has its own back bar, and Escape), failed or expired. There is nothing to add to your page. While the dialog is open the rest of your page is inert and doesn't scroll; both are restored when it closes, and if your page removes the element mid-checkout.

    The element announces the step with natzar:payment (phase: 'started', then 'ended'), handy for analytics. To present the step yourself instead, cancel the start and the widget stays inline:

    el.addEventListener('natzar:payment', (e) => {
      if (e.detail.phase === 'started') e.preventDefault();
    });

    If you do, don't move the element into your own dialog: re-inserting an iframe reloads it, and the checkout in progress goes with it. (A reload never costs the patient a second payment — the checkout is bound to the invite, and pressing again resumes it or, once paid, lets them straight in — but it does make them start the form over.)

    Prescriptions

    When a physician issues a prescription on an async consult, the /pharmacy?id= link in the notice (Prescriptions §1) is resolved inside the widget: both <natzar-async> and <natzar-agent> render the notice as a card with a "Choose a pharmacy" button that opens the picker (list + map, search, add-a-pharmacy where faxing applies) in the same frame, then shows the send outcome. The card stays reachable on the thread's rating and closed screens for as long as the link is valid (24 h), and it re-labels itself ("Sent to …", "Link expired", "Withdrawn") as the prescription moves. No host action is needed — the notice arrives on your webhook as an ordinary async_consult.message with classification: 'async:prescription_*', but the patient never has to leave your page to act on it. The picker's device-location step needs the geolocation delegation described above.

    Token expiry in practice

    Plan for sessions longer than one token lifetime (a patient can sit in a chat or waiting room for a while):

    el.addEventListener('natzar:expired', async ({detail}) => {
      // Your endpoint calls POST /v1/…/{consultId}/embed-session with YOUR key.
      const {sessionToken} = await fetch(`/api/natzar-token?consult=${detail.consultId}`)
        .then((r) => r.json());
      el.refresh(sessionToken);
    });

    Rotating your API key coarsely invalidates outstanding embed tokens (see Authentication) — the same natzar:expired / refresh path covers that too.

    Building your own plumbing

    If you'd rather manage the iframe yourself, the underlying protocol is window.postMessage: the iframe posts envelopes {source: 'natzar-embed', event, data} ( EmbedPostMessage) to its parent. Always check source === 'natzar-embed' AND the message origin before trusting one. The custom elements are exactly this plumbing plus origin checks and the natzar:-prefixed re-dispatch — prefer them.

    If you do build the iframe yourself, give it the same allow="camera; microphone; display-capture; geolocation; payment" attribute the elements set: without it the call has no camera or microphone, the pharmacy picker's device-location step fails silently (no prompt) and falls through to a coarse IP-based location, and the checkout offers no wallets.
